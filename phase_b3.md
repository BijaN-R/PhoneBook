# PROMPT — Phase 3: Optimistic Concurrency, Data Integrity & Seed Cleanup

Continue from Phases 1 and 2.

This phase has two goals:

1. prevent one administrator from silently overwriting another administrator's edits;
2. remove real operational phone-book contacts from EF seed data without deleting existing database data.

Do not introduce distributed locking or pessimistic database locking.

## Concurrency strategy

Use EF Core optimistic concurrency with an application-managed numeric revision.

Add a property named:

`Revision`

Use a 64-bit integer.

Initial revision for a newly created mutable record is 1.

Apply this strategy to all mutable records that administrators can edit:

- PhoneBookGroup
- PhoneBookEntry
- AppSettings
- DocumentHeader if it is editable by the application

Configure Revision as an EF Core concurrency token.

SQLite does not provide a SQL Server-style automatically updating rowversion, so Revision must be incremented by the application only when a successful logical modification is being persisted.

## Application contracts

Application edit models/commands must carry the revision that the administrator originally loaded.

Create or adapt application models such as:

- Group edit/update model with ExpectedRevision
- Entry edit/update model with ExpectedRevision
- Settings update model with ExpectedRevision
- DocumentHeader update model with ExpectedRevision if applicable

Do not expose EF tracking objects to Web.

## Update behavior

For every update:

- load or attach the target record.
- use the originally supplied revision as the concurrency original value.
- write the new values.
- increment Revision.
- save.

If another admin changed or deleted the record after it was loaded, EF must produce a concurrency conflict instead of silently overwriting the newer value.

Translate provider/EF concurrency exceptions into a clean application-level exception/result such as:

`ConcurrencyConflictException`

Web must not display raw EF/SQLite exception details.

## Conflict UX

When a conflict occurs, the admin UI must tell the user that the record has changed since it was opened.

Offer a clear action to:

- reload the latest record

Do not automatically overwrite the newer version.

Do not implement automatic field-by-field merge in this phase.

## Delete behavior

Deletes must also respect ExpectedRevision where practical.

An administrator must not be able to delete a record based on a stale screen after another administrator has changed that record.

## Entry reordering

`MoveEntryAsync` must remain atomic.

The application determines the adjacent neighbor.

Infrastructure performs the order swap in one transaction.

Concurrency must cover both involved records.

If either record changed before the transaction succeeds, abort the operation and return a concurrency conflict.

Because `(GroupId, DisplayOrder)` is unique, retain the safe temporary ordering strategy or replace it with another equally safe transaction strategy.

## Concurrent inserts/order assignment

Two admins may simultaneously create records whose automatic DisplayOrder/Priority is calculated from the same maximum value.

Handle the resulting unique-order race safely.

Use a small bounded retry only for this known ordering race:

- recompute the next value
- retry a limited number of times
- otherwise surface a clean application error

Do not create a generic retry framework.

## Seed cleanup

The current phone-book operational contacts must no longer be EF model seed data.

Remove all real `PhoneBookEntry` records from `HasData`.

Do not retain employee names/extensions in migrations or source-controlled seed definitions.

Do NOT allow the migration generated by this cleanup to delete existing contacts from a real database.

This requirement is critical.

If EF generates `DeleteData` operations merely because old HasData entries were removed, adjust the migration so existing operational rows are preserved while the model snapshot is updated.

## Default groups

Do not keep the complete current organization structure as model seed data.

Replace it with a very small first-run initialization set of common generic groups, only when a brand-new/empty phone book is being initialized.

Suggested default groups:

- مدیریت
- منابع انسانی
- واحد مالی
- لجستیک
- نرم‌افزار پیام کوتاه
- پشتیبانی پیام کوتاه
- واحد IT
- حراست

Keep the list small.

Prefer a controlled `DefaultPhoneBookDataInitializer` in Infrastructure that inserts these groups only when the group table is empty, rather than treating mutable operational organization data as permanent EF `HasData`.

Existing databases containing groups must not be overwritten or supplemented automatically.

AppSettings/default header technical initialization may remain deterministic, but do not overwrite user-modified values.

## Data rules

Preserve existing unique ordering constraints.

Do not add a unique constraint on Extension unless the existing requirements prove that shared extensions are impossible. Shared phone extensions may be legitimate.

Do not convert warning-level duplicates into database errors in this phase.

## Architectural placement

Concurrency exception/result types belong in Application.

EF concurrency configuration and DbUpdateConcurrencyException handling belong in Infrastructure.

UI conflict presentation belongs in Web.

## Out of scope

No audit logging.

No deployment/migration automation redesign.

No broad testing initiative.

No search redesign yet.

No import/export yet.

Do not delete existing user data.

## Completion criteria

The phase is complete when:

- stale admin edits cannot silently overwrite newer edits.
- stale deletes are detected.
- MoveEntry remains atomic and concurrency-safe.
- ordering races on simultaneous insert do not result in silent corruption.
- operational contacts are no longer source-controlled seed data.
- existing databases retain their current contacts/groups.
- a new empty installation receives only a small generic group set.
- the solution builds and existing tests continue to pass.
